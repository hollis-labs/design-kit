# Generic admin shell: placement and composition proposal

**HOLD for Chrispian — CW-20261002-0015, 2026-10-02.** This is a design
proposal, not implementation approval. It recommends **`@hollis-labs/kit-admin`
in design-kit**, consumed by app-owned hosts and generated by Folio. No package,
export, adapter, application migration or release is created here. Approval of
this proposal is a prerequisite for CW-20261001-0512.

The accepted Tesseract ADR `project/design-kit/knowledge/adr:adr_vnext_gui_story`
(item `01M3WAKT94AR27S83XS6ESHGV2`, decision 3 and 4(a)) calls for one
manifest-driven admin experience, configuration only in Settings and runtime
views in Status/Diagnostics. The approved [manifest contract](admin-manifest-contract.md)
and [observation spec](kit-observe-spec.md) own those semantics. Their original
proposal/unmerged headers describe their drafting moment; the current task
records their approval. This document leaves their text and examples unchanged
and records gaps as questions rather than introducing wire fields.

## 2. Gaps and package decision

The missing reusable unit is **the manifest's section renderer and navigation
coordination**. Forms and evidence panels are built; app adapters, compatible
published dependencies and real two-app proof remain. Sharing only a copied
App.tsx would leave section placement, error boundaries and setup reconciliation
to drift independently in each consumer.

| Location option | Fit | What it does not fit |
| --- | --- | --- |
| **New `@hollis-labs/kit-admin` in design-kit — recommended** | One versioned controlled composition with Settings/Status/Diagnostics rules; usable both in standalone generic admin and an existing opinionated app. Real consumers are Tachyon and the planned Nanite helper host. | Adds a package/release surface and depends on currently private kits. It cannot ship through registry consumers until those dependencies are released. The name and creation need Chrispian's approval. |
| App-level composition copied by every app | Quick local wiring; accommodates app routers/auth. | Copies the reusable policy/UI itself, reproducing the divergent pages the ADR rejects. Keep only host adapters and product routes app-owned. |
| Shell implementation owned solely by Folio presets | Easy bootstrap with a Go host and UI. | Generated source is copied, and this preset's sync skips frontend source. Existing/opinionated apps cannot consume one maintained implementation without regenerating or manually reconciling it. Folio should distribute wiring, not own the renderer. |
| Put it in kit-dashboard | Reuses the same chrome without another package. | Makes the dashboard idiom own settings/observation orchestration and private-kit release dependencies; a table/layout consumer would acquire admin coupling. Keep dashboard responsible for its existing layouts and charts. |

**Proposed dependency direction:** kit-admin → kit-settings, kit-observe,
design-components, design-tokens and the existing dashboard navigation/layout
entrypoints. No app, Folio or Go package import; no wire-type registry, resolver,
secret store, router or fetch client inside kit-admin. Wire definitions remain
with `go-envelopes/admin`; future TypeScript projection/generation must be
assigned explicitly rather than cloning the contract in the new package.

The shell's ordinary entrypoint would provide controlled admin navigation and
page composition, without re-exporting sibling components. Keep the optional
series renderer behind a separate `/charts` entrypoint or an explicit supplied
renderer: do not drag a chart engine into Settings-only consumers. The exact
export names are implementation choices after approval, not existing APIs.

Initially create it **private 0.0.0** in the future implementation task. Registry
adoption requires a coordinated, separately approved release of kit-settings,
kit-observe and kit-admin with valid dependency ranges. kit-observe also needs
the dashboard minor containing TimestampSampleChart (merged PR #43, absent from
registry 0.2.0). A workspace demo cannot establish that published consumers
resolve those imports. Require packed-consumer proof and then released versions
before app/Folio adoption. This proposal approves no publish, tag, credentials,
root-workspace edit or package creation.

## 3. Page model and the config-versus-view rule

The meaning of a value determines its destination. **Desired configuration,
including locked env/file-owned values, has one canonical editor under Settings.
Measured/computed runtime state belongs to Status or Diagnostics and has no
configuration mutation controls.** Disabled configuration is still configuration;
read-only appearance alone does not make a value an observation. Desired
`embedding_mode` and computed `embedding_status` are different resources.
Per-field source, validation and `apply_state` are configuration metadata in
Settings, not a copy of process/runtime telemetry.

| Page | Manifest input | Proposed rendering |
| --- | --- | --- |
| Dashboard | `app`, declaration revision and section/resource availability | A read-only **directory/landing page** with app identity and links to canonical pages/groups; no fields, runtime KPI copies or independent resource fetches. V1 has no Dashboard array/section. |
| Settings | `settings` groups with `section: settings` | One provenance renderer per selected group/context, preserving manifest order, scope, source, locks and pending application. Setup is an alternate Settings mode using the same groups/state, not a second editor/navigation category. |
| Status | `health` and `stats`, both `section: status` | HealthSummary and StatCollection with per-resource availability/time, real zero versus missing, and counters labelled cumulative. |
| Diagnostics | `series` and `diagnostics`, both `section: diagnostics` | SampleSeriesView for bounded exact samples; DiagnosticPanel for validated bounded structured data. No inferred streaming log/activity/trace resource. |

Reject contradictory sections rather than moving resources by label. Array
order is display order; stable identities include app, authorized context,
resource kind and ID (IDs are unique within their respective arrays). Missing
arrays are malformed v1; empty arrays are unsupported. Omit empty optional page
links and explain unsupported if a user visits a direct/deep link. Dashboard
remains a directory even for a minimal app; all-empty is “No admin resources
declared”, never “Healthy”. A fetched, supported manifest plus a failed group
read still leaves other groups/resources navigable. First discovery failure is
a global unavailable state; failed rediscovery may retain labelled old content
but suspends writes until declaration/auth context is re-established.

The host owns route prefixes, selected page/group, deep links and browser history;
proposed relative destinations are Dashboard, Settings, Status and Diagnostics
under its chosen admin mount. NavRail receives controlled href/onSelect items.
The host decides whether this composition occupies a whole AppShell or a routed
content region within an existing product shell. Do not nest fixed viewport
shells. Product nav can link to this admin surface but cannot supply a second
settings editor for the same group. Historical routes may redirect to its
canonical Settings group or Status/Diagnostics resource.

### Tether stress test: split semantics, keep one editor

| Current mixed Settings content | Destination after a separately scoped adapter/migration |
| --- | --- |
| Shutdown timeout, permission mode, launch engine/root and editable path/provider scalar configuration | Settings, keyed to the backend's real scope; locked deployment configuration stays here with a reason. |
| PID, uptime, socket/path existence, running/ended session counts, process reachability | Status stats/health or bounded Diagnostics details, according to meaning. A configured path and a check that it exists are distinct resources. |
| Runtime config drift versus desired config source/application | Desired source/pending apply remains in Settings; actual daemon/load evidence lives in Status/Diagnostics with a link back to Settings. Do not repeat editable values as another form. |
| Events, tool calls, scopes, JSON detail | Existing Activity product routes can remain. Only resources actually declared by v1 are rendered generically; do not invent an activity/log manifest array. |
| Reload/apply/deploy, provider create/delete, launch commands, complex onboarding lists/maps, roadmap/product editors | App-owned workflow/product routes. Do not pretend lifecycle or arbitrary CRUD is `update`/`reset`, or coerce collections into the scalar form profile. |

A Status card may link to the one Settings group (“Configure daemon”); it does
not render its fields or save controls. A locked listen address is configuration
in Settings; the observed bound endpoint/socket state is a separate runtime
view. Tether's user/project/global resolver and union/overlay rules stay in the
backend. If a needed mapping is ambiguous, the adapter must label/declare its
semantic resource or leave it unsupported rather than copying the entire mixed
legacy response into both pages.

**Alternative:** Dashboard as health/stat summaries could be convenient, but
would duplicate Status content and loosen the accepted “only Status/Diagnostics”
placement without a Dashboard contract. Recommend the directory for v1; ask
Chrispian explicitly before extending that model.

## 4. Host adapter seam: controlled presentation

The app owns a controller around the proposed renderer. It supplies a validated
manifest projection, selected route/context, settings snapshots/drafts and
sanitized results, independent observation states/data and clock, setup step,
and callbacks for user intents. These are presentation inputs, not new wire
fields. The renderer initiates no discovery, polling or mutations on mount.
The manifest client uses the declared v1 methods/paths. Legacy verb envelopes
and mixed response fields are normalized by backend adapters; the shared kit
does not accumulate Tachyon/Nanite-specific decoders.

| Concern | Host responsibility |
| --- | --- |
| Discovery | Authenticated manifest read at the deployment's configured discovery path; validate v1, IDs, sections, declaration/capability/endpoint consistency and same-origin safe prefixed paths. Unknown contract version blocks all resource rendering/writes. Unsupported group schema disables that group, not supported siblings. A declaration is not a fetched value. |
| Auth/context | Existing app auth, per-call authorization and cookie CSRF rules; caller-filtered manifest. On principal/app/subject change, cancel work and clear snapshots/transient drafts (including secrets). Do not use a stale caller's manifest during reauthentication. No new login/session/role system in the kit. |
| Settings client | Read each selected group, retain its strong ETag separately from the manifest revision. Keys include app + authorized subject + group. Project into SettingsProvenanceRenderer; keep response headers and mutation construction outside it. Validate capabilities locally for feedback and let the backend enforce them again. |
| Commands | User save/validate/reset intent becomes the contract's exact typed request with the current declaration revision; update/reset attach that group's If-Match. Local validation supplements mandatory backend full-config/semantic validation. No speculative success, mutation on discovery, retry timer or cross-group transaction. |
| Apply/lifecycle | Save never restarts. Per-value pending state stays visible until verified. The generic shell declares no restart endpoint. Default omit onApply; an app may explicitly wire the existing controlled apply callback to its separately authorized workflow/approval UI, with host-issued targets and rereads. Plugin recovery and HITL stay app-owned. |
| Observations | One bounded schedule per visible resource; declared poll/stale intervals and series limits, no overlap; cancellation/generation guards for context/revision/filter/range changes. Stop hidden polling; refresh stale evidence on return. Reuse the same host state if a resource is revisited, not independent page schedules. Validate observed timestamps, units, finite values, diagnostic schemas/bounds and sanitized payloads before projection. |
| Partial failure | Separate per-group/per-resource loading, error, snapshot and observed time. Retain successful observations on refresh failure without refreshing their timestamp. A 200/unhealthy is an unhealthy observation; first-fetch timeout/503 is unavailable. Missing/null/empty/truncated/unsupported remain distinct, without default zeros or healthy badges. |

### Revision conflicts and uncertain outcomes

1. Freeze that group's submission when a command returns **409** or **412**;
   re-read the authenticated manifest and affected snapshot/ETag. Invalidate late
   responses from the old declaration/context. A removed permission/group is
   not a reason to replay a write elsewhere.
2. Show an explicit conflict with the new source/locks and safe nonsecret
   before/draft/current values. Preserve compatible nonsecret draft intent only
   for user review; reject incompatible fields and clear secret replacements.
   Revalidate against the new declaration and require a new explicit submit.
   Never overwrite automatically or treat an earlier Validate as permission.
3. On an uncertain network result after a mutation, re-read rather than retry.
   A known rejected mutation can retain the draft/error; an unreadable outcome
   stays uncertain. Clear accepted group drafts only after an authoritative
   outcome/snapshot, and do not tell the user a secret was saved speculatively.
4. Distinguish declaration `revision` from per-group ETag. A truly unchanged
   resulting snapshot may retain its ETag. Command `restart_required`/targets
   describe this command's changes; a subsequent no-op's false/empty aggregate
   must **not** clear earlier per-field pending_restart. Host apply projections
   preserve verified outstanding state rather than copying only the latest
   command aggregate. True restart requirement with no targets is invalid;
   expose an unavailable action, never guess targets.

Point 4 follows the reviewed Go-core behavior at `7cc237c` and the routing in
CW-20261001-0504 comment 8200. CW-20261002-0013 separately owns the planned
clarification note after the HTTP binding lands; this proposal does not edit
approved contract wording or turn response aggregates into new wire fields.

Secrets start as blank replacement controls plus presence/source text. Keep,
replace (including a deliberately typed empty string) and explicit unset retain
the existing semantics. No drafts in URLs, analytics, logs or browser secret
persistence. The host clears secret drafts on accepted save, discard, unmount
and context/declaration invalidation. An expired auth boundary stops callbacks;
hiding navigation is not authorization.

## 5. First run through the existing Wizard

**Recommended:** the host offers “Set up this app” under Settings when its
backend/app policy identifies incomplete first-run configuration, and allows an
explicit operator entry. No new `onboarding` flag or check endpoint is added to
manifest v1; unknown/error snapshots are unavailable evidence, not proof that
setup is needed. Completion is host-owned and context/revision-aware.

Reuse `SettingsWizard` with the same selected manifest groups and host drafts:
required groups first, required fields first, stable order within partitions,
one group per step, then review. The host controls the step; dynamic completion
does not reorder it. Locked settings are explanatory text, secrets are blank
replacements. Complex Nanite/Tether product onboarding remains outside this
scalar wizard.

Connectivity checks are explicit host requests/results, not manifest discovery
probes or background fetching by the kit. Only host `ok` is OK; required checks
block completion until OK and are invalidated after relevant edits/context
changes. Do not invent a check for every group. Resume stores only host-approved
nonsecret state with its context/revision; secret replacements stay transient.

Final completion receives the existing ordered per-group intent array. The host
validates/writes each group with its own revision/ETag, records saved/failed
results independently, updates accepted snapshots and clears only accepted
drafts. There is no all-or-nothing wizard transaction or automatic retry.
A later user submit sends remaining edits after conflict reconciliation.
“Setup saved” does not mean a process restarted or a service is healthy.
Pending application remains in canonical Settings.

The current Wizard does not expose the normal provenance renderer's field/footer
slots. Recommend keeping source/apply summaries in host-provided context beside
the wizard and linking to normal Settings for full provenance. A richer wizard
metadata slot, if required by dogfood, needs its own component decision; do not
silently promise a second provenance form or new Wizard API here.

The **two-app acceptance proof** is the same renderer against real Tachyon
config-ops and real Nanite Go-helper handlers, with different backend adapters.
A fixture/demo or two mounts of one mocked client is not that proof. Both apps
must demonstrate manifest discovery/auth, locked config in Settings, observation
only in Status/Diagnostics, honest partial failure, local group save/conflict
handling and the same controlled first-run intent model. Exercise secret paths
only when implemented with the required guarantee; record disabled capability
as a limit, not a passing writable-secret test. Tether tests the separation
rule but is not substituted for the agreed second helper dogfood.

Future implementation verification should include:

- Computed token styles, readable nav/forms, narrow/wide scrolling, labelled
  controls, keyboard/focus preservation and reduced motion with real packed
  artifacts. The existing AppShell handles viewport sizing; use one scroll owner
  per page and stack groups/panels on narrow widths.
- Initial/refresh failures, stale/null/zero/unhealthy/unknown/truncated samples
  and absent resources, without sibling state contamination or duplicated polls.
- Per-group 409/412 reconciliation, failed validation, effective permissions,
  no-op after pending restart, uncertain writes and context/auth cancellation.
- Wizard resume, invalidated checks, explicit submit, partial group success and
  no automatic restart; secret keep/replace/unset without persistent disclosure.
- Route/resource mapping against Tether's mixed meanings and retained product
  workflows, using behavior examples rather than a mutable-source/count gate.

This docs PR supplies source evidence and a proof plan only. It claims no new
browser, conformance, auth, save/restart, packed shell or application proof.

## 7. Explicitly out of scope

Package creation/code, wire/schema changes, new repo, token/theme changes,
router/auth/credential framework, backend resolution/storage/transactions,
automatic lifecycle actions, generic backup restore/plugin recovery, arbitrary
nested/collection settings, account management, activity/log/trace APIs,
retention/query/aggregation engines, data derived from polling as history,
Tachyon freeze exceptions, app migrations, Folio edits, publishing/tags,
root/lockfile changes and new count/source-agreement checks. Product apps remain
opinionated hosts; the generic admin surface does not replace their workflow UI.
